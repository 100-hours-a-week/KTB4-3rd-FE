# 코드 리팩터링

렌더링, API 변환, 뮤테이션, 내비게이션, 모달 상태, 오류 처리가 한 파일에 섞여 화면을 읽기 어려워진 경우 이 스킬을 사용합니다. 목표는 의도가 드러나는 작은 UI 컴포넌트를 만들고, 동작을 가장 적절한 slice가 소유하도록 하는 것입니다.

## 수정 전 확인

- 파일을 변경하기 전에 저장소의 AGENTS.md와 관련 프레임워크 또는 아키텍처 스킬을 읽습니다.
- 대상 화면, 라우트 진입점, 가져오는 feature/entity slice, API/query 모듈, 기존 테스트와 스토리를 확인합니다.
- 먼저 작업 트리를 확인합니다. 관련 없는 변경을 보존하고, 소유권이 함께 바뀐다는 근거 없이 대규모 이동을 하지 않습니다.
- 동작 계약을 파악합니다. 로딩, 오류, 빈 상태, 성공, 재시도, 내비게이션, 인증, 캐시 업데이트, 포커스와 스크롤 동작을 확인합니다.

## 책임 분리 기준

코드의 크기나 파일 이름이 아니라, 해당 코드가 변경되는 이유를 배치 위치의 기준으로 사용합니다.

다음 질문에 답하면서 소유 레이어를 결정합니다.

- 백엔드 응답 구조나 API 계약이 바뀌면 함께 바뀌는가? → API 타입, query, adapter
- 사용자의 행동이나 비즈니스 규칙이 바뀌면 함께 바뀌는가? → features
- 특정 라우트의 화면 구성이나 레이아웃이 바뀌면 함께 바뀌는가? → _pages
- 여러 화면에서 공유되는 안정적인 도메인 표현이 바뀌면 함께 바뀌는가? → entities
- 제품 도메인과 무관한 공통 UI나 유틸리티인가? → shared

같은 이유로 항상 함께 변경되는 코드는 굳이 나누지 않습니다. 반대로 한 파일 안에 API 변환, 비즈니스 동작, 화면 조합이 서로 다른 이유로 변경된다면 각각의 소유 레이어로 분리합니다.

파일을 짧게 만드는 것이 목적이 아닙니다. 코드를 읽는 사람이 각 동작의 책임자와 변경 위치를 쉽게 알 수 있게 만드는 것이 목적입니다.

### API 데이터와 UI 데이터

실제 데이터 변환이 없다면 매퍼를 추가하지 않습니다. API 응답을 사용하는 도메인과 UI의 필드 이름은 백엔드 명세와 동일하게 유지합니다. 특히 content를 description으로, origin_name을 departure_location으로 바꾸는 것처럼 필드 이름만 바꾸는 매핑은 유지 사유가 아닙니다.

다음 중 하나라도 수행한다면 어댑터를 유지합니다.

- 백엔드 응답을 다른 도메인 의미로 명시적으로 변환합니다. 이 경우에도 API 응답 필드 자체는 백엔드 명세를 유지하고, 별도 도메인 값이나 계산된 값을 추가합니다.
- 부분 응답에 UI 기본값을 채웁니다.
- 요약 응답과 상세 응답을 결합합니다.
- null 가능하거나 선택적인 API 데이터를 정규화합니다.
- 표시를 위해 정렬, 페이지네이션 또는 중첩 레코드를 변환합니다.

이런 어댑터는 큰 ui 파일에서 분리해 소유 slice의 model, lib 또는 endpoint 인접 모듈로 이동합니다. 경계의 의미가 드러나는 이름을 사용합니다. 예를 들어 toPostDetail, toPostComments처럼 작성하고 양쪽 타입을 명시합니다. API 타입이 이미 도메인 또는 UI 계약과 동일하다면, 파일을 하나 더 만들기 위한 무의미한 매퍼는 추가하지 않습니다.

### UI 파일의 핸들러

이벤트 전달, 로컬 disclosure 상태 업데이트, 부모가 전달한 ref 호출처럼 표현 계층의 연결만 담당한다면 UI 파일에 핸들러를 둘 수 있습니다.

인증 가드, 뮤테이션, query 재요청 또는 무효화, 페이지네이션 가드, 스낵바나 피드백 상태, 내비게이션, 재시도 조정처럼 비즈니스 동작이나 여러 부수 효과가 들어가면 핸들러를 분리합니다. 재사용 가능한 사용자 액션에는 feature model hook을 사용하고, 한 라우트의 query를 조합하는 동작에만 해당한다면 page model hook을 사용합니다. UI는 이름이 분명한 작은 명령을 받고, 그 결과 상태를 렌더링해야 합니다.

### 페이지 모델과 도메인 모델의 조합

하나의 페이지 모델이 서로 다른 서비스 도메인의 상세 조회, 뮤테이션, 내비게이션, 캐시 동기화, 피드백 상태를 함께 관리하면 도메인별 page model hook으로 나눕니다. 예를 들어 동행모집과 커뮤니티가 한 페이지의 모달에서 함께 사용되더라도 다음처럼 각 도메인의 변경 이유를 한곳에 모읍니다.

```text
usePageModel
├── useCompanionDomainModel
│   ├── 상세 조회와 상세 어댑터
│   ├── 참여 워크플로와 성공 후 이동
│   └── 참여 오류 상태
└── useCommunityDomainModel
    ├── 상세·댓글 조회와 상세 어댑터
    ├── 댓글 등록 워크플로
    └── 댓글 생성 후 캐시 동기화와 피드백 상태
```

단순히 `handleJoined`, `handleCommentCreated` 같은 콜백만 별도 파일로 옮기지 않습니다. 해당 콜백이 속한 query, mutation, 파생 데이터, 오류·피드백 상태까지 같은 도메인 모델이 소유해야 분리가 의미 있습니다. 페이지 모델은 선택된 리소스, 페이지 공통 상태, 도메인 모델 간 조정, UI에 전달할 최종 계약만 담당합니다.

도메인 모델은 서비스의 모든 내부 정보를 그대로 반환하는 거대한 객체를 만들지 않습니다. 페이지가 실제로 조합해야 하는 최소한의 응집된 계약을 반환합니다. 일반적으로 `detail`, `detailState`, `workflow`, `onRetry`, `onClose`처럼 데이터·상태·명령의 경계를 드러내고, raw query 객체·query key·내부 mutation 객체는 외부로 노출하지 않습니다. 여러 페이지에서 재사용되는 순수 비즈니스 규칙은 page model이 아니라 feature나 entity로 이동합니다.

### 위에서 아래로 읽히는 동작 흐름

컴포넌트와 hook 내부의 코드는 사용자가 동작을 따라가는 순서대로 배치합니다. 일반적인 순서는 입력과 로컬 상태, query와 store 조회, 파생 상태, 사용자 액션 핸들러, 렌더링입니다.

- 페이지 컴포넌트는 화면에 필요한 상태와 데이터를 위에서 선택하고, 아래에서 레이아웃과 하위 컴포넌트를 조합합니다.
- 렌더링 분기는 로딩, 오류, 빈 상태, 성공 상태처럼 실제 화면 상태의 흐름이 드러나도록 배치합니다.
- 핸들러가 호출하는 복잡한 구현은 model, feature, lib로 이동해 UI 파일의 위에서 아래로 읽는 흐름을 끊지 않습니다.
- 같은 파일 안에서도 보조 함수나 세부 구현이 주요 동작 흐름보다 먼저 등장해 읽기를 방해하지 않도록, 주요 흐름을 먼저 보여주고 세부 구현은 적절한 하위 모듈로 분리합니다.

### 모달과 바텀시트 상태

공유 BottomSheet와 BottomModal 프리미티브는 표현 역할만 유지합니다. 라우트별 복구 정책을 공유 UI 컴포넌트에 넣지 않습니다.

화면 전용 시트나 모달의 부모가 다음 관심사 중 둘 이상을 섞고 있다면 책임에 따라 분리합니다.

- 트리거 또는 선택 상태
- query 선택과 데이터 변환
- 로딩, 오류, 빈 상태, 성공 상태 분기
- 액션 콜백과 뮤테이션 피드백

NearbyPostsSheet, PostDetailModal, PostDetailModalContent, PostDetailModalState처럼 역할이 드러나는 컴포넌트를 _pages 조합 계층에 둡니다. 재사용되지 않는 상태 뷰는 모달 가까이에 둡니다. 여러 화면에서 같은 상태 계약을 사용할 때만 공유 상태 컴포넌트로 추출합니다.

## FSD 경계

- 라우트 진입점은 app/에 얇게 두고 _pages의 public API를 조합합니다.
- 화면 조합은 _pages에 두고, 사용자 액션과 비즈니스 워크플로는 features에 둡니다. 안정적인 도메인 표현과 경계 어댑터는 entities에, 도메인과 무관한 프리미티브는 shared에 둡니다.
- 이 프로젝트는 `src/widgets/` 레이어를 사용하지 않습니다. 새 코드를 배치하거나 widgets 레이어를 전제로 한 구조를 만들지 않습니다.
- 같은 레이어의 import나 구현 세부사항을 노출하는 barrel을 만들지 않습니다. 의도적으로 공개할 항목만 slice의 index.ts를 통해 export합니다.
- 파일을 짧게 만들기 위해서만 코드를 옮기지 않습니다. 소유권을 명확히 하거나 중복 동작을 제거해야 합니다.

## 리팩터링 절차

1. 현재 동작을 기록하고 여러 화면에 중복된 흐름이 있는지 찾습니다.
2. 먼저 순수 어댑터를 추출합니다. 입력과 출력 타입을 확인하고, 변환이 복잡하다면 집중된 단위 테스트를 추가합니다.
3. 다음으로 상태가 있는 워크플로를 추출합니다. 뮤테이션 콜백, 인증 확인, 캐시 동기화, 피드백 상태를 함께 유지해 액션의 소유자를 하나로 만듭니다.
4. 큰 모달 또는 시트의 렌더링 분기를 이름이 있는 상태 또는 콘텐츠 컴포넌트로 분리합니다. 데이터와 명령을 props로 전달하고, 표현 컴포넌트가 페이지 query나 store에 직접 접근하게 하지 않습니다.
5. 페이지 컴포넌트를 화면 상태 선택, 레이아웃 조합, 명시적 props 전달만 남도록 줄입니다.
6. public API, 테스트, 스토리, import를 갱신합니다. 호환성을 위한 중복 코드를 남기지 말고 사용하지 않는 코드를 제거합니다.
7. 가장 좁은 범위의 관련 검사를 먼저 실행하고, 가능하다면 저장소에서 요구하는 검사도 실행합니다. 금지된 폴더나 오래된 import가 생기지 않았는지 확인합니다.

## 안전 확인

- 렌더링 동작, 접근성 레이블, 로딩·오류·빈 상태, query key factory, 캐시 무효화 의미를 보존합니다.
- hook 규칙과 client/server 경계를 보존합니다. use client는 필요한 가장 작은 경계에 둡니다.
- 요청에 동작 변경이 포함되지 않았다면 API payload, 라우트 의미, 사용자에게 보이는 문구를 변경하지 않습니다.
- 몇 개의 응집도 높은 모듈을 우선합니다. 각 파일에 변경 이유가 하나씩 명확해지는 시점에서 더 이상 나누지 않습니다.
